# Что нужно собрать перед проектированием UI

Чек-лист документов, без которых дизайнер не сможет спроектировать интерфейс
Domna без домыслов. Составлен по результатам анализа кодовой базы: текущего
проекта `Domna/`, а также двух предшествующих реализаций того же приложения в
`Bloom/` — Slint-версии (`furnace/app/ui/main.slint`, 1167 строк, самая полная
по функциональности) и Qt-версии (`src/gui/main_window/main_window.ui`).

**Как читать статусы:**

* `ЕСТЬ` — документ или его содержимое уже в репозитории, указан путь;
* `СГЕНЕРИРОВАТЬ` — в коде есть всё необходимое, документ можно составить
  самостоятельно и отдать на утверждение;
* `ЗАПРОСИТЬ` — в коде информации нет и быть не может, нужен человек.

---

## Что установлено анализом кода (контекст для дизайнера)

Чтобы список ниже читался правильно, вот подтверждённые фактами свойства
продукта:

* **Однопользовательское десктоп-приложение.** Поиск по всей кодовой базе
  (`auth`, `login`, `role`, `permission`, `HttpClient`, `sqlite`, `postgres`) не
  дал ни одного совпадения. Нет авторизации, ролей, сервера, БД и сети.
  Раздел «права доступа по ролям» для этого продукта пуст — и это факт, а не
  пробел.
* **Один основной сценарий:** ввести 11 параметров → получить 3 температуры и
  3 их отношения. Плюс три надстройки, реализованные в Slint-версии:
  оптимизация (обратная задача), история расчётов, сравнение с базой.
* **Вся история расчётов живёт только в памяти процесса.** Ни в одной из версий
  нет сохранения на диск — закрытие приложения теряет сохранённые расчёты.
* **Данные не приходят извне.** Оператор вводит всё руками; интеграции с АСУ ТП
  печи в коде нет.

## 1. Функциональные требования

### 1.1. Карта пользовательских сценариев (user flows)

* **Назначение.** Задаёт, какие задачи экран должен закрывать и в каком порядке:
  разовый расчёт, подбор параметров под целевое распределение, сравнение
  вариантов. Без неё невозможно расставить приоритеты на экране.
* **Статус.** `СГЕНЕРИРОВАТЬ` — все сценарии восстанавливаются из кода:
  `Bloom/furnace/app/src/app_controller.cpp` (методы `recalc`, `on_optimize`,
  `on_save`, `on_load`, `on_compare`), список коллбэков в `main.slint`
  (`calculate-clicked`, `reset-clicked`, `save-clicked`,
  `optimize-to-baseline-clicked`, `load-history-clicked`,
  `compare-history-clicked`, `clear-history-clicked`) и слоты Qt-версии
  (`main_window.h`).
* **Приоритет.** Критично.
* **Источник.** Код (см. выше) + утверждение у технолога-заказчика: код
  показывает, *что реализовано*, но не *что нужно*.

### 1.2. Портрет пользователя и условия эксплуатации

* **Назначение.** Определяет плотность интерфейса, размер шрифта, контраст и
  способ ввода. Интерфейс для инженера за настольным монитором и для мастера у
  печи — это два разных интерфейса.
* **Статус.** `ЗАПРОСИТЬ` — в коде нет ничего об этом.
* **Приоритет.** Критично.
* **Источник.** Заказчик / технолог доменного цеха. Минимально нужны ответы:
  кто пользователь (мастер печи, технолог, инженер-исследователь), где стоит
  рабочее место, как часто выполняется расчёт, монитор и его разрешение, есть
  ли сенсорный ввод.

### 1.3. Сценарий оптимизации (обратная задача)

* **Назначение.** Самая сложная часть интерфейса: оператор выбирает, какие
  параметры разрешено менять, задаёт целевые отношения температур и получает
  подобранный набор. Нужно описание того, как он мыслит эту задачу.
* **Статус.** `СГЕНЕРИРОВАТЬ` частично — механика в коде есть
  (`Bloom/furnace/engine/include/engine/optimizer.h`: `free_mask`, `OptTargets`,
  детерминированный `seed`), в Slint-версии реализованы флаги «свободный
  параметр» у каждой строки ввода, индикаторы направления изменения
  (`opt-dir-*`: ↑/↓/без изменений) и кнопка «Оптимизация Дельты».
  **Неоднозначность:** движок принимает произвольные целевые отношения, но в UI
  выведен только сценарий «вернуться к базовому расчёту»
  (`optimize-to-baseline-clicked`). Открытый вопрос, а не факт.
* **Приоритет.** Критично.
* **Источник.** Код оптимизатора + продакт/технолог: нужно ли задавать
  произвольные цели вручную.

### 1.4. Подтверждение отсутствия ролей и многопользовательского режима

* **Назначение.** Снимает с дизайнера необходимость проектировать вход,
  профили и разграничение прав.
* **Статус.** `ЗАПРОСИТЬ` (подтверждение). В коде ролей нет ни в каком виде.
* **Приоритет.** Желательно.
* **Источник.** Заказчик — одной строкой: «приложение однопользовательское,
  вход не требуется».

### 1.5. Требования к экспорту, печати и протоколированию расчётов

* **Назначение.** Определяет, нужны ли кнопки выгрузки, форма протокола и
  экранная вёрстка под печать.
* **Статус.** `ЗАПРОСИТЬ` — в коде экспорта нет ни в одной из версий, при этом
  есть история расчётов, что косвенно указывает на потребность их куда-то
  девать.
* **Приоритет.** Желательно.
* **Источник.** Заказчик / технолог.

## 2. Информационная архитектура

### 2.1. Карта экранов и навигации

* **Назначение.** Фиксирует, сколько экранов в приложении и как между ними
  переходят.
* **Статус.** `СГЕНЕРИРОВАТЬ` + **конфликт, требующий решения.** Две
  реализации спроектированы противоположно:
  * Qt-версия — многостраничный мастер: `QStackedWidget` со страницами
    `results_page`, `snapshots_page`, `compare_page`, кнопки «Рассчитать»,
    «Сравнить», «Назад» (`main_window.ui`);
  * Slint-версия — один экран-дашборд: параметры слева, результаты, графики и
    история одновременно на экране, пересчёт по каждому изменению
    (`auto-calc`).
  Текущая Domna следует второй схеме.
* **Приоритет.** Критично — это развилка, определяющая весь дизайн.
* **Источник.** Оба файла разметки + решение продакта/заказчика.

### 2.2. Приоритеты информации на главном экране

* **Назначение.** Что читается первым: абсолютные температуры или их отношения.
* **Статус.** `СГЕНЕРИРОВАТЬ` — ответ следует из предметной области:
  `docs/domain-model.md` объясняет, что оператор управляет *формой* газового
  потока, и именно отношения описывают форму, а уровень температур следует за
  тепловым балансом. Модель и подогнана под два отношения напрямую.
* **Приоритет.** Критично.
* **Источник.** `docs/domain-model.md` + подтверждение у технолога.

### 2.3. Структура блока «История расчётов»

* **Назначение.** Определяет карточку сохранённого расчёта и операции над ней.
* **Статус.** `СГЕНЕРИРОВАТЬ` — структура записи полностью определена:
  `struct HistoryEntry` в `main.slint` (метка + 3 температуры + 3 отношения),
  правило именования — `Bloom/src/core/utils/common_utils.h`
  (`Snapshot #001 | 14:30:45`), операции — загрузить, сравнить, очистить.
* **Приоритет.** Желательно.
* **Источник.** Код (см. выше).

### 2.4. Словарь терминов и экранных подписей (RU)

* **Назначение.** Единые формулировки названий параметров, единиц и
  сокращений. Без него на макетах появятся три разных названия одного поля.
* **Статус.** `СГЕНЕРИРОВАТЬ` + **расхождение.** Существуют три набора подписей
  для одних и тех же полей: краткие в `main.slint` («Уровень засыпи, м»),
  развёрнутые в `main_window.ui` («Фактический уровень засыпи», «Содержание
  железорудного материала в шихте по станциям углового положения лотка,
  №№ 3-5») и текущие в
  `Domna/src/Domna.UI.ViewModels/ParameterLabels.cs`. Плюс сокращения на
  результатах: Тц, Тгр, Тпер, Тц/Тгр, Тпер/Тц, Тпер/Тгр.
* **Приоритет.** Критично.
* **Источник.** Три файла выше; утверждает технолог — формулировки отраслевые.

## 3. Данные и состояния

### 3.1. Спецификация полей ввода

* **Назначение.** Единицы, диапазоны, значения по умолчанию, разрядность — всё,
  из чего собирается форма ввода.
* **Статус.** `ЕСТЬ` — `Domna/docs/domain-model.md` (таблица 11 параметров) и
  `Domna/src/Domna.Domain/Parameters/ParameterCatalog.cs`.
* **Приоритет.** Критично.
* **Источник.** Готово, дополнительных действий не требуется.

### 3.2. Спецификация выходных значений и форматов

* **Назначение.** Что показывать, с какой точностью, в каких единицах, как
  выглядит «значения ещё нет».
* **Статус.** `СГЕНЕРИРОВАТЬ` — состав выходных данных описан в
  `docs/domain-model.md`; форматы восстанавливаются из кода: температуры с
  одним знаком и суффиксом `°C`
  (`Domna/src/Domna.UI.ViewModels/TemperatureReadingViewModel.cs`), заглушка до
  расчёта — `–` (`main.slint`), дельты относительно базы — отдельной строкой.
* **Приоритет.** Критично.
* **Источник.** Код + утверждение точности у технолога.

### 3.3. Матрица состояний интерфейса

* **Назначение.** Закрывает пустые состояния, ошибки, загрузку — то, что чаще
  всего забывают и что потом всплывает в разработке.
* **Статус.** `СГЕНЕРИРОВАТЬ` — подтверждённые кодом состояния:
  * значений ещё нет (`–` во всех полях результата);
  * параметр вне диапазона обучения — рамка и текст поля красные
    (`border-oor #e03030`), общее предупреждение «⚠ Значение вне диапазона
    данных обучения»;
  * история пуста — «Нет сохранённых расчётов»;
  * идёт сравнение — выделена сравниваемая запись, показаны дельты;
  * **не покрыто ни одной реализацией:** индикация выполнения оптимизации.
    Оптимизатор — это дифференциальная эволюция плюс Нелдер–Мид в многораундовом
    цикле; операция заведомо не мгновенная, но ни прогресса, ни блокировки, ни
    отмены в UI нет.
* **Приоритет.** Критично.
* **Источник.** `main.slint`, `app_controller.cpp`,
  `Bloom/furnace/engine/src/optimizer.cpp`.

### 3.4. Поведение при некорректном и выходящем за диапазон вводе

* **Назначение.** Определяет, что происходит по мере набора текста: блокировать
  ввод, подсвечивать, показывать сообщение, запрещать расчёт.
* **Статус.** `СГЕНЕРИРОВАТЬ` + **три несовместимых поведения в коде:**
  * Qt — `QDoubleValidator` с отложенной валидацией и авто-подсказкой
    диапазона в placeholder (`numeric_line_edit.h`), кнопка расчёта блокируется
    (`onUpdateCalculateButtonState`);
  * Slint — свободный текстовый ввод, значение вне диапазона только
    подсвечивается, расчёт выполняется;
  * Domna сейчас — обычный двусторонний биндинг без валидации вовсе.
* **Приоритет.** Критично.
* **Источник.** Три файла выше; решение принимает продакт совместно с
  технологом (см. также 4.2 — политика экстраполяции).

### 3.5. Разрядность и округление

* **Назначение.** Сколько знаков после запятой показывать и принимать в каждом
  поле.
* **Статус.** `СГЕНЕРИРОВАТЬ` + **расхождение.** В каталоге Domna разрядность
  задана по-разному для разных параметров (1–3 знака, поле `Decimals`), а в
  Qt-версии у всех одиннадцати параметров стоит `5`
  (`Bloom/src/core/utils/parameter_utils.h`). Какая точность осмысленна
  физически — вопрос к технологу, а не к дизайнеру.
* **Приоритет.** Критично.
* **Источник.** `ParameterCatalog.cs`, `parameter_utils.h`, технолог.

### 3.6. Замер времени работы оптимизатора

* **Назначение.** Ответ на вопрос, нужен ли прогресс-индикатор, кнопка отмены и
  блокировка интерфейса, или результат появляется мгновенно.
* **Статус.** `СГЕНЕРИРОВАТЬ` — измеряется на существующей C++-реализации до
  переноса на C#.
* **Приоритет.** Желательно (становится критичным, если время > 300 мс).
* **Источник.** `Bloom/furnace/engine/src/optimizer.cpp`, разработчик.

## 4. Бизнес-ограничения

### 4.1. Регламент границ параметров

* **Назначение.** Границы определяют и валидацию, и подписи «допустимый
  диапазон» под каждым полем.
* **Статус.** `ЗАПРОСИТЬ` — **конфликт уже зафиксирован** как открытый вопрос
  в `docs/domain-model.md`: в двух предшествующих проектах для одних и тех же
  параметров заданы разные пределы (например, уровень засыпи 1.25–3.10 против
  1.25–2.46; крупность агломерата 9.74–11.69 против 9.94–10.67). Какой набор
  соответствует реальной области обучения — из кода не следует.
* **Приоритет.** Критично.
* **Источник.** Автор регрессионной модели / технолог.

### 4.2. Политика экстраполяции

* **Назначение.** Разрешено ли считать вне области обучения. От этого зависит,
  предупреждение это или запрет — и, соответственно, весь дизайн валидации.
* **Статус.** `ЗАПРОСИТЬ`. Текущее поведение Domna: считать и пометить как
  экстраполяцию (зафиксировано в `AGENTS.md` как красная линия), но это
  инженерное решение, а не утверждённое требование.
* **Приоритет.** Критично.
* **Источник.** Заказчик / технолог.

### 4.3. Достоверность модели: происхождение и подача

* **Назначение.** Определяет, показывать ли оператору качество прогноза и как.
  Число без меры доверия оператор либо переоценит, либо проигнорирует.
* **Статус.** `ЗАПРОСИТЬ`. В Slint-версии в подвале зашита строка
  `R²(Тц) = 0.854   R²(Тц/Тгр) = 0.842   R²(Тпер/Тц) = 0.785   N = 336`.
  Откуда эти значения, к какой печи и какому периоду относится выборка из 336
  наблюдений — нигде не задокументировано. Это дополняет открытый вопрос 2 в
  `docs/domain-model.md`.
* **Приоритет.** Критично.
* **Источник.** Автор модели.

### 4.4. Ограничения на целевые значения оптимизации

* **Назначение.** Какие сочетания целевых отношений физически достижимы, что
  показывать, если цель недостижима.
* **Статус.** `ЗАПРОСИТЬ` — в коде валидации целей нет; оптимизатор молча
  возвращает ближайший найденный набор, и по возвращённому значению нельзя
  отличить точное попадание от «дальше не смог».
* **Приоритет.** Желательно.
* **Источник.** Технолог + разработчик (нужна ли выдача остаточной невязки в UI).

## 5. Технические ограничения

### 5.1. Инвентаризация UI-стека и переиспользуемых компонентов

* **Статус.** `СГЕНЕРИРОВАТЬ` — стек подтверждён: C# / .NET 10 / WPF, MVVM на

* **Источник.** `.csproj`-файлы, `Theme.xaml`.

### 5.2. Решение по визуализации (графики и тепловая карта)

* **Источник.** `main.slint` (как референс), решение разработчика: библиотека

### 5.3. Целевая платформа, разрешение и размеры окна

### 5.4. Требования к локализации

* **Статус.** `ЗАПРОСИТЬ`. В Qt-версии была заготовка под перевод
  (`QTranslator`, `Bloom_ru_RU.ts`), но файл перевода **пустой** — механизм не
  использовался. В Domna подписи заданы по-русски прямо в коде
  (`ParameterLabels.cs`).
* **Приоритет.** Опционально.
* **Источник.** Заказчик.

### 5.5. Требования к читаемости в условиях цеха

* **Назначение.** Минимальный кегль, контраст, дистанция чтения, освещённость.
* **Статус.** `ЗАПРОСИТЬ` — производная от 1.2.
* **Приоритет.** Желательно.
* **Источник.** Заказчик / охрана труда цеха.

## 6. Брендинг и дизайн-система

### 6.1. Решение по визуальной теме

* **Назначение.** Базовая развилка оформления, от которой зависит вся палитра.
* **Статус.** `ЗАПРОСИТЬ` (решение) — **в коде два противоположных варианта:**
  * Slint-версия — тёмная промышленная тема: фон `#1a1f2e`, панели `#232a3e`,
    карточки `#2d3650`, акцент янтарный `#f0a500`;
  * Domna сейчас — светлая: фон `#F7F7F5`, панели белые, текст `#1F1E1C`
    (`Themes/Theme.xaml`).
* **Приоритет.** Критично.
* **Источник.** Заказчик; при отсутствии предпочтений — решение дизайнера с
  учётом 5.5.

### 6.2. Брендбук предприятия

* **Назначение.** Логотип, корпоративные цвета, шрифты, если приложение
  внедряется на конкретном комбинате.
* **Статус.** `ЗАПРОСИТЬ` — в репозитории нет ни логотипа, ни шрифтов, ни
  упоминаний бренда.
* **Приоритет.** Желательно.
* **Источник.** Заказчик.

### 6.3. Каталог компонентов дизайн-системы

* **Назначение.** Описание всех повторяющихся элементов: строка ввода
  параметра, карточка результата, чип отношения, строка истории, индикатор
  дельты. Составляется после 6.1.
* **Статус.** `СГЕНЕРИРОВАТЬ` (дизайнером). Полный перечень компонентов уже
  известен из Slint-версии: `InputRow`, `TempBar`, `RatioChip`, `HeatZoneRow`,
  `HistoryRow`, `RadialProfileChart`, `FurnaceHeatmap`.
* **Приоритет.** Критично.
* **Источник.** `main.slint` как перечень; оформление — дизайнер.

### 6.4. Семантика цвета данных

* **Назначение.** Цвет здесь несёт смысл, а не украшает: три зоны измерения
  имеют устойчивые цвета, есть шкала «холодно → горячо» и цвет нарушения
  диапазона. Их нельзя переназначать произвольно.
* **Статус.** `СГЕНЕРИРОВАТЬ` — в Slint-версии закреплено: центр `#e05010`,
  гребень `#d09000`, периферия `#2090d0`; градиент тепловой карты
  `#1a6fb0 → #e0a000 → #e83010`; выход за диапазон `#e03030`.
* **Приоритет.** Критично.
* **Источник.** `main.slint` (`global Theme`, `global Heat`) + проверка на
  контраст и на различимость при дальтонизме.

### 6.5. Набор иконок

* **Назначение.** Иконки действий: сохранить, сравнить, загрузить, очистить,
  оптимизировать, направление изменения параметра.
* **Статус.** `ЗАПРОСИТЬ` / `СГЕНЕРИРОВАТЬ` — в репозитории есть ровно одна
  иконка (`Bloom/resources/icons/right_arrows.png`); в Slint-версии направления
  показаны текстовыми стрелками.
* **Приоритет.** Желательно.
* **Источник.** Дизайнер, после утверждения 6.1.
